# Forge Action: технический R&D

Дата: 24 сентября 2026 года. Статус: техническая проверка выполнена; генерация кода с реальной моделью заблокирована отсутствием доступа к Simple Forge.

## Краткий вывод

Forge организует выполнение задач из GitHub с помощью Claude: получает контекст задачи, подготавливает рабочую ветку, запускает модель, обрабатывает результат и сохраняет изменения. Исследуемый репозиторий — интеграция GitHub Actions, а не весь сервер Forge.

Для пилота инструмент требует доработок и независимой проверки результатов. Найдены воспроизводимые ошибки статусов выполнения и подсчета токенов. В текущем состоянии нельзя считать зеленый workflow доказательством успешного исправления задачи, а отображаемые токены и модель — надежными измерениями.

Полноценный E2E-тест не проведен: нет Forge API key, реального job_id и настроенного доступа к модели. Время генерации, реальные токены, стоимость, качество кода и лупы модели не измерены. Подставные ответы и скрипты используются только для тестирования инфраструктуры и явно обозначены ниже.

## Насколько сложно развернуть

**Если есть готовый доступ к Forge: умеренно сложно.** Нужны Linux runner с Docker, workflow, доступ к тестовому GitHub-репозиторию, Forge API key и задача в очереди Forge. Доступ к Claude идет через Forge AI gateway либо через отдельный Anthropic API key. README допускает JWT, подходящий одновременно для Forge и шлюза, но выдача такого JWT не проверена.

**С чистого GitHub-репозитория: запуск не самостоятельный.** Репозиторий не содержит сервер Forge и инструкцию полного его развертывания. Пустой GitHub-репозиторий подходит как место для тестового проекта, но не создает учетную запись Forge и очередь заданий. В интерфейсе Forge обнаружен ввод готового API key, самостоятельной выдачи ключа в просмотренных экранах нет. Официальная документация указывает контакт `support@simple-container.com`.

**На Windows локально: неудобно.** Наличие Git Bash позволяет проверять обвязку, но не заменяет Linux-контейнер, сервер и ключи. Dockerless тоже требует Docker для извлечения `/app/scripts`. Скрипт установки называет поддержку Windows экспериментальной.

В примерах workflow есть лимит 30 минут. Внутри образа одна попытка Claude допускает 4500 секунд (75 минут). Это разные ограничения: внешний workflow может завершить выполнение раньше внутреннего timeout.

## Основные дефекты и ограничения

### 1. Критично: Dockerless скрывает ошибку обязательного шага

В конструкции `if ! command; then handle_error ... $?; fi` значение `$?` относится к инверсии `!` и равно 0. Обработчик вызывает `exit 0`. Подтверждено во всех 11 обязательных шагах, включая запуск Claude, git push и обновление контекста. При этом `status=success` не записывается: GitHub может видеть успешный shell step с пустыми outputs, хотя задача оборвалась.

Исправление: сохранять оригинальный exit code в ветке `else` без `!` либо явно возвращать ненулевой статус. Добавить регрессионные проверки всех обязательных шагов. Дефект относится к исследованному Dockerless-оркестратору; в entrypoint контейнера обязательные ошибки обрабатываются отдельными `exit 1`.

### 2. Высокий приоритет: метрики токенов ненадежны

`update-context.sh` суммирует usage всех JSON-строк без различения промежуточных сообщений и итогов. На искусственном потоке с повторенными итогами подтвержден двойной счет. Если usage нет, расчет идет по длине текста / 4, причем output оценивается по сгенерированному самим скриптом summary. Поэтому токены могут появиться даже без ответа модели.

В отправляемом объекте нет признака `estimated`, cache read/write tokens и стоимости. Все фактические выводы о расходе должны опираться на сырые usage провайдера и отдельный учет каждой попытки. Нельзя делать финансовые выводы из текущего dashboard без сверки.

### 3. Высокий приоритет: выбранная модель не прослеживается до вызова

Action объявляет `model_name=claude-sonnet-4-5` и передает `MODEL_NAME`. В извлеченных скриптах `/app` не найдено чтение `MODEL_NAME`; Claude вызывается без `--model`, но с `--fallback-model sonnet`. При переходе root → `su - claude-agent` entrypoint явно не переносит ни `MODEL_NAME`, ни `ANTHROPIC_BASE_URL`.

Это статически подтвержденная неполная передача настройки, а не измерение реально выбранной модели. Реальная модель может зависеть от CLI/config/gateway. Если модель не найдена в ответе, отчетность подставляет `claude-3-5-sonnet-20241022`; это значение не является доказательством ее использования.

### 4. Высокий приоритет: fallback теряет код ошибки Claude

В `retry_claude_fallback` используется pipeline `claude | tee | while ...` без `pipefail`. Ошибка первого процесса может превратиться в успех pipeline. Это воспроизведено на точной извлеченной функции. Последующие проверки всего скрипта иногда могут обнаружить пустой ответ, поэтому результат этого опыта не означает, что абсолютно любой сбой всего Docker Action будет скрыт.

### 5. Средний приоритет: сохранение контекста с HTTP 401 завершается успешно

`update-context.sh` сообщает об ошибке, но не возвращает ненулевой код. Подтверждено подмененным ответом HTTP. Состояние сервиса может расходиться с фактическим состоянием workflow.

### 6. Воспроизводимость и старт

- `@v1` указывает на изменяемую ссылку, а Docker Action внутри использует `:latest`. Даже фиксация commit Action не фиксирует образ.
- `acquire-scripts.sh` ищет релиз в `simple-container-com/simple-forge-action`, а проверяемый проект называется `forge-action`. Проверенный URL отвечает 404, после чего используется latest.
- `setup-claude.sh` пытается поставить CLI 2.1.39 через npm, но при отсутствии npm или ошибке переходит на установщик latest. В истории сборки образа установки Node/npm не видно. Фактическая версия CLI после полного setup не измерена.
- Dockerless — исполнение вне контейнера после извлечения скриптов через Docker, а не отсутствие зависимости от Docker.

### 7. Логи и очистка: замечания по коду

В `execute-claude.sh` отладочный вывод `${API_KEY:+<set>}${API_KEY:-<not set>}` дописывает значение ключа, если он установлен. Реальный ключ для проверки не использовался. GitHub может маскировать зарегистрированные secrets, но полагаться только на это нельзя. Следует выводить только факт наличия ключа.

Dockerless записывает GitHub token в глобальную конфигурацию и `~/.git-credentials`; cleanup удаляет `.simple-forge`, но явно не очищает эти credentials и рабочую `.forge-tmp`, которую используют скрипты из образа. Cleanup выбирает все контейнеры по ancestor образа, а не только контейнер текущей задачи. Для self-hosted runner это риск остаточных секретов и вмешательства в соседний запуск. Эти пункты выявлены чтением кода, опасные операции на машине пользователя не запускались.

## Повторы, timeout и лупы

В `execute-claude.sh` есть streaming-цикл максимум на 3 попытки при двух конкретных ошибках согласованности tool use; между ними sleep 2 секунды. После ошибки предусмотрен buffered fallback, также с числом попыток до 3, и финальная минимальная попытка. Еще есть диагностический запрос к Claude при пустом fallback-ответе. Поэтому нельзя свести верхнюю стоимость к «одному запросу» или считать простую сумму 3+3+1 строгим числом всех обращений.

Основной streaming-вызов не содержит `--max-turns` и `--max-budget-usd`. В fallback стоят 35 turns / $2, в финальном режиме 35 turns / $1. Это аргументы отдельных вызовов, а не общий проверенный бюджет job. Фактическое соблюдение лимитов моделью/шлюзом не тестировалось.

`monitor-claude.sh` опрашивает состояние раз в 30 секунд в `while true`; основной скрипт останавливает его после завершения исполнения. Наличие этого цикла не означает зацикливание модели. Автоматического семантического детектора повторяющихся безрезультатных действий в просмотренной обвязке не найдено.

Дополнительный риск по коду: streaming parser запускается один раз на FIFO, а повторная попытка пишет в тот же pipe после возможного выхода reader на EOF. Потенциальное зависание открытия FIFO не покрывается timeout самой команды. Это гипотеза по коду, отдельно не воспроизведенная в Linux; не включена в число подтвержденных отказов.

## Подготовленный стенд и следующий этап

### Можно ли самостоятельно скачать сервер и обойтись без hosted Forge

Проверены шесть публичных репозиториев организации: `api`, `welder`, `forge-action`, `go-aws-lambda-sdk`, `actions`, `.github`. Репозиторий `api` скачан на commit `5252819589f8c11f4a4a450c1dbcc4602e1913cb`: это CLI Simple Container для развертывания инфраструктуры, не backend Forge. Welder — инструмент контейнерных сборок.

В [Roadmap репозитория actions](https://github.com/simple-container-com/actions#roadmap) авторы прямо относят `forge` и `forge-conductor` к приватным репозиториям. В публичном Docker Hub namespace `simplecontainer` обнаружены шесть образов: `cloud-helpers`, `caddy`, `kubectl`, `github-actions`, `forge-action`, `chrome-base`. Публичный сервер Forge и готовый комплект self-hosted-развертывания там не обнаружены. Это вывод по проверенным источникам, а не доказательство отсутствия закрытых или иных каналов поставки.

Для собственного полного сервера нужно запросить у авторов доступ к исходникам/образам и инструкции self-hosting. Имитировать API Forge для тестирования wrapper технически возможно, но это не воспроизводит очередь, авторизацию, хранение контекста и всю серверную логику настоящего продукта. Такая имитация не может заменить полноценный R&D Forge. Отдельно требуется доступ к модели, даже если сервер будет свой.

В тестовом репозитории создан небольшой Node.js-проект с двумя намеренными дефектами: расчет стоимости без количества и смещение пагинации. Проверен baseline: 6 тестов, 3 проходят и 3 падают. Эти дефекты внесены для будущей проверки агента и не являются дефектами Forge.

После получения доступа необходимо подключить репозиторий в Forge, создать настоящую задачу/job и выполнить минимум три повторения каждой задачи на одном baseline commit. Для сравнения моделей сначала исправить или подтвердить передачу `model_name` и записывать фактический model ID из ответа провайдера.

Для каждого прогона сохранить: commit и image digest, job/run ID, запрошенную и фактическую модель, времена очереди/setup/генерации/проверки, исходные и итоговые тесты, diff, все попытки/ошибки, input/output/cache usage и подтвержденную стоимость. При повторении одной ошибки и действия три раза без изменения состояния остановить исследовательский прогон и зарегистрировать предполагаемый луп. Внешний timeout и лимит расходов задавать на весь эксперимент.

Пока доступ отсутствует, честный итог — **технический R&D с воспроизведением дефектов, а не полноценный benchmark AI-агента**.
